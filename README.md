# LeadDesk Mini

A small lead-capture product: a public intake form and a password-protected
admin ledger for triaging submissions.

Built for the Digital Heroes Full Stack Development qualification task
(Task A + Task B).

## Stack

- **Next.js 16** (App Router, TypeScript) — one codebase for the public
  page, the admin UI, and the API routes.
- **Supabase** — Postgres database + built-in auth (chosen from the task's
  allowed list).
- **Tailwind CSS v4** for styling.
- **Zod** for validation, shared between the client form and the API route.

## Data model

One table, `leads` (see `supabase/schema.sql`):

| column        | type      | notes                                      |
|---------------|-----------|---------------------------------------------|
| id            | uuid      | primary key, generated by Postgres         |
| name          | text      | required                                    |
| email         | text      | required                                    |
| budget_range  | text      | one of 4 preset ranges                     |
| message       | text      | required, 10–2000 chars                    |
| status        | text      | `New` \| `Contacted` \| `Closed`, default `New` |
| created_at    | timestamptz | set once on insert                        |

Row Level Security is on for the whole table:

- The `anon` role (the public form, unauthenticated) can only **insert**.
  It cannot read or update rows, so a submitter can never see other
  people's leads.
- The `authenticated` role (a signed-in admin) can **select** and
  **update**. Nothing else is granted, so a compromised anon key alone
  can't be used to read the ledger.

Status is constrained at the database level with a `check` constraint, not
just in application code, so a bad request can never write an invalid
status.

## Auth approach

Admin auth uses **Supabase Auth** (email + password) rather than a
hardcoded credential:

1. `middleware.ts` runs on every `/admin/*` request. It reads the Supabase
   session from an httpOnly cookie and redirects to `/admin/login` if
   there's no valid session — the admin page itself is a Server Component
   that never renders for a logged-out request.
2. Signing in (`/admin/login`) calls `supabase.auth.signInWithPassword`,
   which sets a secure, httpOnly session cookie. The app never touches or
   stores the password itself.
3. The `PATCH /api/leads/:id` route re-checks `supabase.auth.getUser()`
   independently of the middleware, so the write path is safe even if it's
   ever called directly instead of through the UI.
4. RLS (above) is the second, database-level layer: even a valid session
   only grants what the `authenticated` policies allow.

There's exactly one admin account, created manually in the Supabase
dashboard (Authentication → Users → Add user) — there's no public sign-up
route, since this is a single-operator admin desk, not a multi-tenant app.

## Running locally

```bash
npm install
cp .env.local.example .env.local   # fill in your Supabase URL + anon key
npm run dev
```

Then, in the Supabase SQL editor, run `supabase/schema.sql` once to create
the table and policies, and add one admin user under Authentication →
Users.

## Deploying

1. Push this repo to GitHub.
2. Create a free Supabase project → run `supabase/schema.sql` in its SQL
   editor → add one admin user.
3. Import the repo into Vercel → add `NEXT_PUBLIC_SUPABASE_URL` and
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` as environment variables → deploy.
4. Test from a fresh/incognito browser: the public form should work with
   no login, and `/admin` should redirect to `/admin/login` until you sign
   in with the admin account created in step 2.

## What's intentionally out of scope

Given the ~5–7 hour estimated effort, a few things were kept simple on
purpose rather than gold-plated:

- Single admin role — no per-admin permissions or invite flow.
- No email notifications on new leads.
- No pagination on the ledger (fine at demo scale; would add
  keyset pagination before this saw real lead volume).
